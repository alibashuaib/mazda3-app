<objective>
Make the Phase 2 approval gate understand the three new proposal kinds (`part`, `failure`, `car_model`) end to end in SQL: live tables, submit with validation and materiality, approve, stale refusal, revert, bulk refusal for new cars, and a server-side baseline of today's catalog.js prices.

Purpose: every Phase 4 slice (parts/prices, community, new models) flows through this gate. The seven hard-coded `schedule_item`/`recall` spots live in the same SQL functions, so they are changed once here instead of three times across slices (MVP exception: shared schema gate, justified by file-level coupling; see RESEARCH Pattern 2).
Output: schema additions, seed generator + generated seed, SQL + static tests.

Research recommendations adopted (open questions):
- Q4: seeded prices get `price_basis 'static'` (unlabelled in UI), or `'dealer'` where catalog.js took the price from the Mazda KSA dealer list. Only `'indicative'` is labelled.
- Q5: an ALT (`alt:<brand-slug>`) proposal requires the part name to already exist for that car in catalogue_parts (any slot).
- Q3: `price_observations` is not used by the gate (excluded from D-13; handled in 04-04).
</objective>

<interfaces>
Proposal shapes this plan defines (consumed by 04-04..04-09):

| kind | car_model_id | target_key | after |
|------|--------------|-----------|-------|
| part | `<modelId>:<engine-slug>` | `<Part Name>|oem` or `<Part Name>|alt:<brand-slug>` | `{tag:'OEM'|'ALT', brand, part_no, price, price_basis:'dealer'|'indicative', note, fitment?}` |
| failure | `<modelId>:<engine-slug>` | issue_key slug `^[a-z0-9-]{1,60}$` | `{title, summary, typical_km|null, mentions}` |
| car_model | null | proposed id `<model-slug>-<start-year>:<engine-slug>` | `{make, model, generation, engine, oil_capacity_l, warranty_years, warranty_km, markets[], years[]}` |

Evidence item types: existing `{url (https), quote, tier, content_hash?}`; NEW `{type:'users', tier:'community', users:int>=3, median:numeric}` (no url, no user ids), allowed only for part/failure.

catalogue_parts columns: car_model_id, part_name, slot, brand, part_no, price numeric(10,2) null, price_basis ('dealer'|'indicative'|'static'), note, sources jsonb, updated_at; PK (car_model_id, part_name, slot).
known_issues columns: car_model_id, issue_key, title, summary, typical_km int null, mentions int >=3, sources jsonb [{url,host}], updated_at; PK (car_model_id, issue_key).

catalog.js facts (src/data/catalog.js): `sharedParts(modelId, engineCode)` returns parts `{name, options:[{tag,brand,partNo,price,store,note,catPrice?}]}`; OEM note contains 'Mazda KSA dealer price list' when DEALER_PRICE supplied the price; `catalogId(modelId, engineName)` L644; `CAR_MODELS[].engines` = [[engineName, oilL]].
